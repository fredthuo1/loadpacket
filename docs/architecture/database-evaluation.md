## Evidence and recommendation

Ordinary PostgreSQL HA inside one region preserves familiar semantics but asynchronous cross-region replicas do not establish this contract. AWS documents asynchronous RDS read-replica replication; a regional outage can precede replica catch-up. This rules out that approach for the stated requirement, not PostgreSQL itself. [RDS replication](https://aws.amazon.com/rds/faqs/)

Native PostgreSQL can wait for remote WAL durability using synchronous standbys; `remote_apply` additionally waits for visibility on the standby. `ANY n` counts servers, not distinct regions: placement and failover policy must ensure a qualifying remote domain, including after promotion. Do not use `remote_write` as proof of durable OS-crash-safe flush. A strict design needs a fenced single writer, non-bypassable commit settings, monitored lag, no automatic async downgrade, eligible-standby promotion and a three-domain control plane. [PostgreSQL synchronous replication](https://www.postgresql.org/docs/current/warm-standby.html)

CockroachDB provides configurable regional survival; the documented five-voter regional layout spreads voters so a single region does not contain a majority. Use region survival, not an assumed default zone-survival deployment. Strong SQL reads and successful quorum commit are required. [Multi-region overview](https://docs.cockroachlabs.com/docs/stable/multiregion-overview), [replica placement explanation](https://www.cockroachlabs.com/blog/under-the-hood-multi-region/)

YugabyteDB DocDB uses Raft replication; evaluate one synchronous universe across three regions, not asynchronous xCluster as an RPO-0 substitute. Master/control-plane and each tablet's data quorum must both survive. The published Prisma example establishes an integration path, not compatibility with this repository's exact ORM/driver/migrations. [Replication](https://docs.yugabyte.com/stable/architecture/docdb-replication/replication/), [Prisma example](https://docs.yugabyte.com/stable/develop/drivers-orms/orms/nodejs/ysql-prisma/)

**Recommendation:** preserve PostgreSQL/Prisma while running a gated comparison. First ask managed PostgreSQL vendors to demonstrate supported strict cross-region commit/fencing; reject regional-HA-plus-async proposals. In parallel within the future POC, evaluate CockroachDB as the explicit region-survival alternative and YugabyteDB as the PostgreSQL-oriented alternative. Prefer a supported managed PostgreSQL solution if it passes all durability/operability gates with the fewest code changes. If none qualifies, select a distributed candidate only after real-schema tests, support and total-cost review. Do not force self-managed HA on a small team merely to retain syntax. No candidate is approved today; see [database ADR](../adr/0003-database-strategy.md).

## Repository compatibility blockers

- Transaction advisory locks and `hashtextextended` occur in signatures, vault, Finance/import services and the historical/live-duplicate trigger. Exact lock scope/serialization must be preserved. Yugabyte migration guidance flags advisory-lock limitations/preview behavior; never silence unsupported-lock errors. Test the pinned release, not a generic “Postgres-compatible” assertion. [Yugabyte migration limitations](https://docs.yugabyte.com/stable/yugabyte-voyager/known-issues/postgresql/)
- `SELECT ... FOR UPDATE`, raw UUID casts, concurrent duplicate detection, trigger-raised SQLSTATE 23505/23514 and Prisma error translation are correctness dependencies. Lock tests must use multiple independent connections/sites.
- PL/pgSQL triggers protect Finance amounts, duplicate history and signature immutability; RLS/revocations deny public Data API access. CockroachDB support varies by release; do not assume absence or full equivalence. Prove exact functions, UPDATE/DELETE policy, triggers and grants or redesign safely before migration.
- Prisma requires its CockroachDB connector for that engine; native type mappings and provider-specific migration history need explicit conversion. Preserve original history and develop a separate validated target baseline, never delete the repository migrations. [Prisma CockroachDB](https://docs.prisma.io/docs/orm/v6/overview/databases/cockroachdb), [provider-specific migration limitation](https://www.prisma.io/docs/orm/v7/prisma-migrate/understanding-prisma-migrate/limitations-and-known-issues)
- UUID, enum, Decimal(12,2), Date, timestamp, Bytes, JSON filters, expression/partial indexes, composite foreign keys, `finance_records` SQL view, collations and case-insensitive matching require round-trip/constraint tests. Import bytes can amplify replicated DB cost.
- Distributed serialization/deadlock retry needs bounded jitter and deterministic callbacks. Current callbacks containing storage/email I/O cannot simply be replayed. Prisma 7.10.0 adapter compatibility and connection pooling must be proven without upgrading dependencies in this ticket.

## POC contract: LP-PROD-002

Use isolated synthetic databases and approved non-production infrastructure in a later task. Pin engine/server/adapter versions; record all topology/settings and quote category costs. No customer dataset, lower-environment production credentials or paid provisioning is authorized here.

1. Apply the real schema and all 17 migrations; record every unsupported statement. For a new connector, produce a reviewed equivalent baseline and compare constraints/views/triggers to source. No disabling tests, locks or integrity constraints to get green.
2. Run the real full LoadPacket regression with a reviewed dedicated POC target wrapper; the current Finance wrapper is intentionally hardcoded to local PostgreSQL and must not accidentally test the wrong engine. Also run explicit constraint tests for every schema safeguard.
3. Record acknowledged operation IDs/hash/amount/version/object receipts in an independent test ledger. Kill the writer and a region immediately before/during/after commit, partition A from B+C, delay packets, expire leases, force DNS staleness and restart clients. Every observed success must exist exactly once on surviving authoritative state. Unknown outcomes must reconcile using the same key.
4. Verify no minority writes, no split-brain promotion, no async fallback, no stale reads used for balances/authorization. Test the administrative promotion path as well as automatic failover.
5. Measure normal and one-region-down p50/p95/p99 commit latency, conflicts/retry rate, throughput, pool saturation and large imports. Initial acceptance budgets proposed: p95 ordinary mutations <=1.5s, p99 <=3s at twice measured launch peak, zero correctness failures. Adjust budgets explicitly before approving tests, never by changing durability.
6. Restore PITR and independent backup with keys into isolation; reconcile all documents/signatures/decimal totals. Demonstrate under-60s safe serving failover and under-15m warm DR or record the achieved limit as a blocker.
7. Produce vendor-supported topology, runbook, failover/fencing proof, migration/backout plan and cost estimate. Architect/SRE/security/product sign-off changes ADR status; a CRUD example cannot.
